# Практика по SQL

## Что нужно

Docker с `docker compose`. Больше ничего — ни Postgres, ни Python ставить не надо.

## Запуск

```bash
docker compose pull && docker compose up
```

Открыть **http://localhost:8766**: список заданий, редактор SQL, проверка.

`pull` нужен каждый раз, когда вам выдали новый комплект: версия образа
закреплена подвижным тегом, и без него docker молча поднимет тот образ,
который уже лежит на диске, — хоть месячной давности.

Порт занят другим приложением — задайте свой:

```bash
PORT=9000 docker compose up
```

## Как это устроено

- **Ваша база живая.** Выполняйте что угодно, включая `INSERT`, `UPDATE`, `CREATE`.
  Открытое задание сразу получает свой пример данных; меню «База» у редактора
  переключает примеры, перезагружает данные и очищает базу. Свои изменения данных
  без спроса не затираются.
- **Проверка идёт в отдельной чистой базе**, на десятках вариантов данных — ваши
  эксперименты ей не мешают. Если решение падает на скрытом варианте, его данные
  можно раскрыть и разобраться.
- **Решения лежат в `solutions/`**, по файлу на задание. Это и есть то, что вы
  сдаёте — коммитьте папку в свой репозиторий.

## Проверить всё разом, как это сделает преподаватель

```bash
docker compose run --rm runner runner ci --pack /pack.enc --solutions /solutions
```

Команда возвращает ненулевой код, если хоть одно задание не зачтено.
Ровно её гоняет CI (GitLab CI) при каждом пуше — результат виден на странице пайплайна.

## Обновление

```bash
docker compose pull && docker compose up
```

Данные вашей живой базы переживают перезапуск (том `pgdata`).

Практика собрана на более новой версии образа, чем у вас, — в списке заданий
появится «Обновите практику». Это как раз про `docker compose pull`.

## Файлы

| Файл | Что это |
| --- | --- |
| `docker-compose.yml` | запуск; здесь же меняется версия образа |
| `pack.enc` | практика: задания, схема, данные. Двоичный, не редактировать |
| `solutions/` | ваши решения |
| `.gitattributes` | защищает `pack.enc` от порчи git-ом. Не удалять |
